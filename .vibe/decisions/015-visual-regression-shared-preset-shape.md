# Visual regression: duck-typed shared preset, dev-preview promoted to a committed fixture, release-gate scope only

**Context:** Backlog item `013` (roadmap decision `024-visual-regression-testing-via-playwright-screenshots.md`) asks for a shared Playwright screenshot-comparison config/fixture that this repo and 7 consuming apps will all extend, plus this repo's own first suite of component-level baselines against `dev-preview/`. Two things surfaced while scoping this that the backlog item's own description didn't anticipate: `dev-preview/` is currently listed in `.gitignore` as a "throwaway local harness... never committed", so a fresh CI checkout would not have it at all; and this repo's only CI pipeline (`release.yml`) triggers solely on tag push, not on every push/PR to `main`.

**Decision:**
- **Duck-typed shared preset, no `@playwright/test` dependency in this package.** `src/testing/visual-preset.ts` exports a plain `createVisualProjectConfig(overrides)` function returning a plain object (viewport, locale, screenshot diff threshold) shaped to match a Playwright config's `use`/`expect` fields, and a `waitForVisualReady(page)` helper typed against a minimal structural interface (`{ addStyleTag, evaluate }`) rather than importing `Page` from `@playwright/test`. A consuming app's real Playwright `Page`/config objects satisfy these shapes automatically; no version-locked dependency (peer or otherwise) on `@playwright/test` is introduced by this package. This also keeps the preset's own logic testable with plain Vitest mocks, consistent with this repo's existing pure-logic/DOM-glue split.
- **The preset is its own Vite lib entry and package export subpath** (`./testing/visual-preset` → `dist/visual-preset.js`), separate from the main `.`/`src/index.ts` bundle. A consuming app's `playwright.config.ts` runs in a plain Node context — importing the main entry would drag in every Web Component and `src/index.ts`'s CSS side-effect import for no reason, and CSS has no meaning to resolve outside a bundler/browser. Kept in sync with `src/publish/validate-pack-file-list.ts`'s expected-file gate, the same guard that already exists to catch exactly this kind of built-output drift.
- **The browser locale is pinned (`en-US`) as part of the shared `use` defaults.** Confirmed during this item's own runtime check: a headless Chromium's default `navigator.language` is not guaranteed to be English (it resolved to French in this sandbox), and `<wuik-locale-switcher>`/any i18n-aware component renders different text depending on it — an unpinned locale is exactly the kind of environment-dependent nondeterminism decision `024` is trying to eliminate, on par with the font-loaded wait and forced-off animations it already calls for.
- **`dev-preview/` is promoted from a gitignored dev-only harness to a committed, permanent fixture.** It is now the visual regression test target — CI needs it in a fresh checkout — and it gains a small dedicated Vite dev-server config (`vite.dev-preview.config.ts`, `npm run dev-preview`) since none existed before (it was previously opened ad hoc).
- **Animations/transitions are force-disabled via injected CSS (`waitForVisualReady`), not `use.reducedMotion`.** `reducedMotion: "reduce"` only helps if a component explicitly honors `prefers-reduced-motion`, which isn't guaranteed here; an injected `* { animation-duration: 0s !important; transition-duration: 0s !important; }` rule is unconditional and matches decision `024`'s explicit "animations/transitions forced off" wording.
- **Baselines cover one default-theme screenshot per component group**, not every attribute-variant/theme combination shown in `dev-preview`. Matches the item's acceptance criteria literally (catch a shared-token/component regression) without exploding the baseline count; per-variant/per-theme coverage is left as a natural follow-up, not fabricated here.
- **The CI gate is scoped to `release.yml` only** (runs before `npm publish`, blocks a release on a diff) — this repo has no push/PR-triggered workflow at all today, for this or any other check (`npm test`/lint aren't gated on push either), so adding one is a separate, larger change outside this item's scope. This means a visual regression can land on `main` and only surface at release time, which is an explicit, accepted limitation, not an oversight.
- **CI pins the exact `@playwright/test` version, the runner OS (`ubuntu-24.04`, not `ubuntu-latest`), and caches `~/.cache/ms-playwright` keyed on that version** — browser-build and OS-image drift are the most common source of false-positive diffs for this kind of test.

**Reason:** The duck-typed shape avoids forcing 7 consuming apps into this package's chosen `@playwright/test` version the moment they extend the preset — each app keeps full control of its own Playwright version. Promoting `dev-preview/` to a committed fixture is a correction, not a stretch: the item explicitly asks to use it "as the real target instead of building a separate harness," which is only possible if CI can see it. Scoping the gate to the release pipeline keeps this item's footprint matching what it actually asked for (`npm run test:visual` as its own CI job/script) instead of silently expanding into "add push/PR CI to this repo," a decision the Product Owner hasn't made.

**Rejected alternatives:**
- **A real Playwright `test.extend()` fixture** (rather than a plain `waitForVisualReady` function) — rejected: `.extend()` requires importing the actual `test` object from `@playwright/test`, which would force a real dependency (peer or direct) on a specific major version, exactly what the duck-typed approach avoids.
- **Declaring `@playwright/test` as a `peerDependency`** — rejected for the same reason: unnecessary now that the shared module has no import-time dependency on it at all; nothing here needs a peer contract.
- **Deep, per-field merge of the whole config object in `createVisualProjectConfig`** — rejected in favor of a shallow merge one level into `use`/`expect`: a consuming app either wants the shared default entirely or fully overrides a specific field (e.g. its own `baseURL`); silently merging nested Playwright-internal sub-objects field-by-field adds complexity with no concrete need behind it.
- **Adding a push/PR-triggered CI workflow as part of this item** — rejected as scope creep: no such workflow exists in this repo (or any repo in the org) today for any check; introducing one is an org-wide CI posture decision, not a side effect of this backlog item.
