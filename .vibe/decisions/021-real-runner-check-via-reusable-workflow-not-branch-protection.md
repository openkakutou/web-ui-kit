# Real-runner baseline check moved earlier via a push/PR-triggered CI workflow, not branch protection

**Context:** Backlog item `022` was opened after four consecutive tagged releases (`v0.8.0`–`v0.11.0`) each failed to publish because a `dev-preview`-touching change carried a stale or only-local-provisional visual-regression baseline, discovered solely by the tag-triggered `Release` workflow's own visual-regression step — after the version had already been git-tagged, leaving a permanent unpublishable tag/release behind each time. `.vibe/decisions/015` originally scoped the real-runner check to the release gate only, explicitly deferring a push/PR-triggered gate as a separate, larger change.

**Decision:**
- The test/lint/visual-regression check is extracted out of `release.yml` into its own reusable workflow, `.github/workflows/verify.yml` (`on: workflow_call`), run on the same pinned `ubuntu-24.04` runner. Both a new `.github/workflows/ci.yml` (triggered on every push to any branch and every pull request) and `release.yml` itself now call this one shared workflow rather than each keeping its own copy of the steps — the two can no longer drift into checking different things, closing off the "two independent copies of the Playwright setup silently diverge" risk a duplicated-steps approach would carry.
- `release.yml`'s own job is split in two: `verify` (calls the shared reusable workflow) and `release` (`needs: verify`, keeps the build/pack/smoke/publish steps). The release job cannot run — and therefore cannot publish — unless the shared real-runner check passes for that exact commit, on that exact tag push.
- This makes the always-on `ci.yml` push/PR check (not a GitHub branch-protection required-status-check) the earlier gate: because it fires on every push to any branch, a stale/provisional baseline is now flagged immediately, well before any later commit tags that same state for release — visible in the repository's own Actions history with no special configuration.
- `CLAUDE.md`'s Definition of Done gets a line calling out this exact check for any change touching `dev-preview/` or a visual baseline, so a future `vibe:feature`/`vibe:fix` run reads it as part of its normal context and follows it without being told.

**Reason:** A reusable-workflow extraction is the standard, zero-duplication GitHub Actions mechanism for "the same check must run in two different trigger contexts" — cheaper to keep in sync forever than two hand-maintained copies of the same steps, which is exactly the kind of drift this item exists to prevent. Firing the check on every push instead of relying on GitHub branch-protection status checks matches this repo's actual workflow: every commit here (including the automation's own `vibe:auto`/`vibe:feature`/`vibe:release` runs) is pushed directly to `main`, never through a reviewed pull request that a required-status-check could gate — a branch-protection rule would therefore only ever apply to a hypothetical future external contributor's PR, not the failure mode these four incidents actually were.

**Rejected alternatives:**
- **Configuring GitHub branch-protection required status checks on `main`** — rejected as the primary mechanism: required status checks only block a *pull request merge*, not a direct `git push` to the branch, and every incident here was a direct push by the project's own automation, not a merged PR. Left as a possible future addition once/if this repo adopts a PR-based flow, not fabricated now to look more "structural" than it would actually be.
- **Duplicating the test/lint/visual-regression steps verbatim into both `ci.yml` and `release.yml`** — rejected: this is exactly the two-copies-drift risk raised during expert review; a reusable `workflow_call` workflow gives one source of truth for free at no cost beyond one extra file.
- **Folding the real-runner check only into `vibe:feature`/`vibe:fix`'s own Definition of Done (option (a) alone, per the backlog item's notes), with no CI safety net** — rejected as insufficient on its own: it is exactly the discipline every one of the four prior incidents already required and still missed; a CI check that runs regardless of whether an implementer remembers is the actual structural fix, with the Definition of Done line added as reinforcement, not as the sole mechanism.
- **Path-filtering `ci.yml` to only run when `dev-preview/` or component files change** — rejected: `.vibe/decisions/017` already showed a baseline can shift from a change to an unrelated page section (scroll offset), so scoping the trigger to an allowlist of "obviously relevant" paths risks silently missing exactly the class of regression this item exists to catch.
