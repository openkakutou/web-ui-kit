# i18n integration layer: shared instance, dual namespaces, decoupled locale-change bus

**Context:** Backlog item `011` adds the shared i18next integration layer and `<wuik-locale-switcher>` called for by roadmap decision `023-localization-approach-for-web-ui.md`. It must let a consuming app configure its own catalog without colliding with `web-ui-kit`'s own translated strings (the shortcuts panel, slider/color-picker invalid-state text), and those existing standalone components must keep working with zero i18n setup at all, matching their "usable standalone" design.

**Decision:** `initI18n({ namespace, resources })` creates one `i18next` instance per app, with the app's own catalog loaded under its own `namespace` and `web-ui-kit`'s own English/French catalog always merged in under a fixed, reserved `wuik` namespace — so both catalogs live in the same instance without key collision, and `web-ui-kit`'s own strings are available in every consuming app with no extra configuration. Detection order is `["localStorage", "navigator"]` with `caches: ["localStorage"]`, so a persisted manual override always wins over browser auto-detection on reload. Standalone components (`<wuik-shortcuts-panel>`, `<wuik-slider>`, `<wuik-color-picker>`) read their own text through a small `t(key, defaultValue)` helper that returns `defaultValue` verbatim whenever no app has called `initI18n()` yet — so nothing about their existing zero-setup behavior changes for a consumer that never touches i18n. Those components, plus `<wuik-locale-switcher>` itself, subscribe to a small internal `EventTarget` bus that `initI18n()` wires to the instance's own `languageChanged` event, rather than importing i18next's instance object directly — decoupling "does text need to re-render" from "which concrete i18next instance is currently active," since the instance is only created once `initI18n()` runs, after components may already be mounted.

**Reason:** A per-app instance (rather than one process-wide global) matches how these apps are actually deployed — one `web-ui-kit` copy per app bundle, never several apps sharing a page — and keeps the mechanism a plain library call with no singleton-registration ordering to get right across separately-built apps. Namespacing over separate instances keeps `web-ui-kit`'s own catalog trivially available everywhere without every consumer having to also configure and load it themselves. The `defaultValue`-returns-untranslated-text fallback (rather than i18next's own key-echoing default) is what keeps existing standalone component tests and usage completely unaffected until an app opts in.

**Rejected alternatives:**
- *A single global default-exported i18next instance, initialized once at module load* — rejected: cannot express "each app supplies its own namespace/catalog" without either a mandatory init call before any import side effect runs, or global mutable config passed some other way; a factory function called explicitly by the consuming app is simpler and matches the kit's existing "call an init/constructor, get an instance" shape (`ShortcutManager`, `CommandStack`).
- *Components import the i18next instance directly and call `instance.on("languageChanged", ...)` themselves* — rejected: couples every text-bearing component to instance identity/lifecycle (which doesn't exist yet at their construction time, and could theoretically be re-created), instead of one indirection point (`initI18n` wiring the bus) that isolates that concern.
- *Have `initI18n` throw a warning by refusing a `namespace` that collides with `wuik`* — rejected as unneeded runtime validation for a developer-time configuration argument, documented instead via JSDoc.
