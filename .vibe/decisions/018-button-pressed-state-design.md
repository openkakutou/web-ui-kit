# `<wuik-button>`'s `pressed` attribute: `aria-pressed` forwarding and pressed-color derivation

**Context:** Backlog item 015 adds a `pressed` boolean attribute to `<wuik-button>` so toggle-style/selectable-list-item buttons across the org (`lifebar-viewer-web`'s elements panel, `character-viewer-web`/`character-editor`'s sprite browser toggle) can stop hand-rolling a raw `<button>` with a custom `is-selected`/`is-active` class and a manually-set `aria-pressed`. Two points needed a deliberate choice: how `aria-pressed` is forwarded to the native button when `pressed` is absent, and how the pressed background color is derived without a dedicated token or a hardcoded literal.

**Decision:**
1. **`aria-pressed` forwarding is asymmetric, not a mirrored boolean.** When the host has `pressed`, the native button gets `aria-pressed="true"`. When it does not, `aria-pressed` is **removed** from the native button entirely — never set to `"false"`. A plain `<wuik-button>` that never uses `pressed` therefore never exposes `aria-pressed` at all, so it is never mistakenly announced as a toggle button.
2. **The pressed background is `color-mix(in srgb, <variant-background-token> 85%, var(--wuik-color-text))`**, applied per variant (`primary`/`secondary`/`danger`), plus a uniform `inset` `box-shadow` using `color-mix(in srgb, var(--wuik-color-text) 35%, transparent)` as a shape/depth cue independent of hue. `disabled` needs no special-case interaction: its existing `opacity: 0.5` + `pointer-events: none` rule already applies on top of whichever background/shadow is active, so a `pressed` + `disabled` button still shows its pressed shape (satisfying the requirement that disabling a selected toggle doesn't silently un-select it visually) while still reading as unmistakably disabled overall (satisfying the requirement that disabled visually dominates) — no extra CSS rule needed for the combination.

**Reason:**
1. `aria-pressed`'s mere presence (true *or* false) changes a control's accessible role to a toggle button per the WAI-ARIA authoring practices. `<wuik-button>` is used for both plain actions ("Save", "Cancel") and, from this feature on, toggles — across roughly seven consuming apps. Always forwarding `"true"/"false"` (mirroring how `disabled` is forwarded unconditionally today) would silently turn every existing plain button in the org into an ARIA toggle. Only ever adding the attribute when actually pressed keeps every non-adopting button's accessibility tree completely unchanged; the cost — an unselected toggle-style item is a plain button rather than an explicit "toggle, not pressed" — is a strictly smaller and easier problem, and is the direction WAI-ARIA guidance and the consulted UX expert both endorse. Concrete first adopters that today always set `aria-pressed="false"` on unselected items (e.g. `lifebar-viewer-web`) are expected to change that call, not be mirrored — that pattern is itself the anti-pattern this feature exists to correct.
2. Mixing in `--wuik-color-text` was checked numerically (not assumed) against every variant's actual token values in both themes: for `primary`/`danger`, the on-color text sits at the opposite luminance extreme from `--wuik-color-text`, so the mix *raises* contrast against the existing on-color text token; for `secondary` (background and text both already involve `--wuik-color-text`-adjacent tokens) the mix *lowers* contrast versus the current 16:1 baseline, but only down to ~11.8:1 (light) / ~10.5:1 (dark) at the chosen 85/15 ratio — nowhere near the 4.5:1 floor. A single ratio across all three variants was kept deliberately, trading perfectly uniform perceived "pressedness" for a simpler, one-rule-per-variant implementation; the `run` skill's real-browser smoke pass is the actual check for whether the result reads as visually distinct, not the contrast math alone.

**Rejected alternatives:**
- Always forwarding `aria-pressed="true"/"false"` unconditionally (mirroring `disabled`) — rejected: converts every plain, non-toggle `<wuik-button>` in the org into an ARIA toggle button, a false and unwanted semantic change with a much larger blast radius than the problem being solved.
- A dedicated `--wuik-color-pressed`/`--wuik-color-*-pressed` token pair — rejected as unnecessary token surface area for a single-component visual variant; revisit if a second, unrelated component later needs the same "pressed" concept.
- Per-variant tuned mix ratios instead of one constant 85/15 — rejected for now as disproportionate polish for a single attribute feature; the uniform ratio already clears the contrast bar comfortably for all three variants.
- Relying on the pressed background color alone (no shape cue) — rejected: fails the "not color alone" requirement flagged during expert consultation, since `secondary`'s existing border is itself already partly a non-color signal that a pure background-color pressed state would compete with rather than reinforce.
