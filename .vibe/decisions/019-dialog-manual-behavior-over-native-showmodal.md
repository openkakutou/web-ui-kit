# `<wuik-dialog>`'s focus trap, Esc, and backdrop-click are hand-rolled, not left to native `showModal()`

**Context:** Building `<wuik-dialog>` (backlog item `016`) on top of a real `<dialog>` element so consumers get `showModal()`'s focus trap, `::backdrop`, and Esc-to-close "for free". Verified directly against this repo's own test environment (Vitest + jsdom 25.0.1): `typeof HTMLDialogElement.prototype.showModal` is `"undefined"` — jsdom does not implement `showModal()`/`close()`/the modal state at all, only the plain `open` attribute. None of the "for free" behavior the backlog cites is observable, or even callable, under the test runner every other component in this kit is verified through.

**Decision:** `<wuik-dialog>`'s `open` reflected attribute is the single source of truth for open/close state; `showModal()`/`close()` methods and the `open` property are thin wrappers that set/remove it. The attribute's `attributeChangedCallback` transition runs the component's *own* JS for every behavior the backlog asks for: capturing the triggering element, moving focus to the first focusable element, trapping Tab/Shift+Tab by always computing next/previous focus from its own list (never relying on the browser's default tab order or on `inert` being applied to the rest of the page), closing on Escape (`document`-level capturing keydown listener) and on a genuine backdrop click (a `mousedown`+`click` origin check on the internal `<dialog>` element, so a text-selection drag started inside and released outside is not misread as a backdrop click), and restoring focus to the trigger (skipped if it's no longer connected). Separately, and only as a rendering enhancement, the internal `<dialog>` calls native `showModal()`/`close()` when they exist, to get the real `::backdrop` paint and top-layer stacking in actual browsers — but nothing about the component's *observable contract* depends on that call succeeding. The close button is placed last in DOM/tab order (absolutely positioned to its conventional top-right spot), so Tab from the dialog's first slotted control reaches the close button last rather than first.

**Reason:** Every target consumer is an evergreen browser that supports `showModal()` fully, so production correctness is unaffected either way. But the kit's own tests run under jsdom, which cannot exercise `showModal()`'s native inert/focus-trap/backdrop behavior at all — a design leaning solely on it would be unable to prove any of the acceptance criteria under this repo's test conventions (`CLAUDE.md`: tested through the public contract under jsdom), and would ship the component's most important behavior "verified" only by a one-off manual smoke pass. Hand-rolling the behavior in component JS, with the native call as a pure enhancement, makes every acceptance criterion independently testable under jsdom today, and behaves identically regardless of whether the browser's native modal path is available — matching the precedent in decision `006` (real-rendering correctness is confirmed once via the `run` skill's runtime smoke check, not asserted by the unit suite) without giving up jsdom coverage of the actual interactive logic, since here — unlike `006`'s CSS case — the logic itself, not just its rendered result, can be expressed in plain testable JS.

**Rejected alternatives:**
- *Rely purely on native `showModal()` for focus trap/Esc/backdrop, matching the backlog's "for free" framing literally* — rejected: unverifiable by this repo's test suite (jsdom has no implementation to exercise), leaving the component's core behavior untested by anything but a manual pass.
- *Switch this component's tests to a real browser environment (Playwright/`@vitest/browser`)* — rejected for the same reason decision `006` rejected it for CSS: disproportionate, project-wide cost to fix a gap that only affects this one component's native-API dependency.
- *Focus the close button first (literal DOM-first element) since it is the first thing rendered* — rejected: landing every dialog's first Tab stop on "close" before any real content is a worse default than reaching the dialog's own content first; the close button is real but deliberately last in tab order instead, while remaining visually first (top-right) via absolute positioning.
