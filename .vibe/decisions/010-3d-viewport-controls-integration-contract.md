# 3D viewport controls extend the transform+event contract to orbit cameras, with a distinct WebGL-unsupported state

**Context:** Building `<wuik-viewport-3d>` (backlog item `007`) — reusable orbit/pan/zoom camera controls for `stage-viewer-web`/`stage-editor` to preview Ikemen GO 3D model-based stages (roadmap decision `014`). The sibling 2D control (`<wuik-viewport>`, decision `008`) already established that this kit's viewport controls never own rendering: they compute a transform and hand it to the consumer via a getter + change event, touching no pixels. The question was whether that same philosophy extends cleanly to a 3D orbit camera, and how to handle a browser/environment with no WebGL support, which has no 2D equivalent.

Two consulting experts (UI/UX, frontend design) were brought in on the plan before implementation; their input shaped the decisions below.

**Decision:**
- `<wuik-viewport-3d>` owns only camera *math* — spherical coordinates (azimuth, elevation, distance from a target point) — never a WebGL context, a renderer, or the consumer's scene graph. It exposes the current camera as a snapshot (`target`, `distance`, `azimuth`, `elevation`, derived `position`) via a getter and a `wuik-viewport3d-change` event, mirroring decision `008` exactly. Any actual 3D rendering (three.js, raw WebGL, or otherwise) is entirely the consumer's responsibility.
- Interaction split follows the conventional orbit-camera pattern used by Sketchfab/Blender/Google Earth/most three.js `OrbitControls`-based tools, per the UX consultation: primary-button drag orbits; either a Shift-held primary drag or a secondary (right) button drag pans, so both a modifier-key and a no-modifier path exist. This is a deliberate departure from the 2D sibling's single-drag-does-one-thing model, because a 3D orbit camera genuinely has two independent free axes of drag-driven motion (orbit, pan) where 2D pan is the only drag gesture that needs one.
- Zoom dollies the camera toward/away from the *target point* (changes distance only), not toward the cursor. Cursor-relative zoom in 3D would require unprojecting the screen-space cursor into world space — typically via a depth read or a ray/scene intersection — which needs knowledge of the consumer's actual 3D scene that this component deliberately does not have (same "no rendering ownership" boundary as decision `008`). Target-relative dolly is the same behavior most orbit-camera libraries default to for exactly this reason.
- Elevation is hard-clamped away from the poles (a fixed, non-configurable epsilon margin) so the camera can never flip past top/bottom-dead-center and invert its apparent rotation direction — the UX consultation flagged this as the orbit-specific analogue of the 2D sibling having no such degenerate case. This is a correctness clamp, not a configurable option: no acceptance criterion calls for tuning it, and exposing it as configurable purely to reach the poles would reintroduce the very disorientation it exists to prevent.
- Pan distance is **not** bounded to a radius around the initial target, unlike distance and elevation. The component has no notion of the consumer's actual scene scale or bounds (it never reads the scene), so any numeric limit would be arbitrary and could clip legitimate exploration of a large stage. The mitigation the UX consultation converged on instead: a reset-to-default-view action must be trivially easy to find, so getting lost is always one obvious action away from fixed, never a dead end requiring the keyboard shortcut to be known. Concretely, the component always renders its own visible "Reset view" button as built-in shadow-DOM chrome (not left to a consumer's optional `overlay` slot), in addition to the `0`/`Home` keyboard shortcut and the `resetToDefault()` method — mouse-only and keyboard-only users each have a direct path back.
- A discoverability hint (drag/shift-drag/scroll legend) is rendered as visible built-in chrome by default, not hidden behind a screen-reader-only instructions paragraph the way the 2D sibling's is — the 2D sibling's single always-obvious drag-to-pan gesture doesn't need a sighted-user hint, but this component's two-drag-gesture split (orbit vs. pan) and focus-gated wheel are genuinely undiscoverable to a sighted mouse user without one, per the UX consultation. It is dismissed after the first successful orbit/pan/zoom interaction on that instance, matching a standard one-time coachmark, and is rendered as an opaque pill (background token, not bare text) so it never becomes unreadable over bright rendered content, per the frontend-design consultation.
- A missing-WebGL-support environment gets a **visually and semantically distinct** fallback from the existing malformed-configuration invalid state (decision `007`'s pattern): a neutral/muted border and `role="status"`, not the danger-adjacent `aria-invalid` treatment — per the frontend-design consultation, "no WebGL" is an environment fact the consumer cannot fix by correcting an attribute, whereas the existing invalid-state convention exists specifically for user/config-correctable mistakes. Conflating the two would make that distinction meaningless the moment both exist side by side. The fallback fills the component's box with an explicit surface-token background (this component, unlike the 2D sibling, has content behind it — the fallback message itself — that must never render on an unpainted/transparent ground), states plainly that 3D preview is unavailable in this browser/environment, and suggests a concrete next step (update the browser / enable hardware acceleration) rather than a bare "unsupported" label with no path forward. Orbit/pan/zoom controls and the reset button are not rendered in this state, since there is nothing for them to act on.
- An on-screen 3D axis/compass gizmo is explicitly deferred, not built now — no acceptance criterion requires it, and per the frontend-design consultation, if ever added it must be DOM/CSS chrome layered over the component (reusing the same "overlay" pattern the 2D sibling already has, so `stage-viewer-web`/`stage-editor` don't each invent their own), never drawn into the consumer's WebGL canvas.

**Reason:** Keeping camera math as the entire integration surface (no rendering ownership) preserves this kit's core commitment (decision `011` at the org level, decision `008` locally) to stay technology-agnostic — `stage-viewer-web` and `stage-editor` are free to choose three.js, raw WebGL, or anything else without this component caring. The interaction and fallback refinements above all trace directly to concrete, named risks raised by the two expert consultations (gimbal lock, getting lost with no bounded recovery, conflating environment failure with user error, invisible-until-discovered gesture split) rather than being spec'd speculatively — each addresses a specific failure mode named in that consultation, not a hypothetical one.

**Rejected alternatives:**
- *Cursor-relative zoom (unproject cursor into 3D space, dolly toward that point)* — rejected: requires depth/scene knowledge this render-agnostic component does not have; target-relative dolly delivers the acceptance criteria without that coupling.
- *Bounding pan distance to a fixed radius around the initial target* — rejected: the component has no notion of the consumer's actual scene scale, so any numeric bound is arbitrary and risks clipping legitimate use; an always-visible, trivially-reachable reset action addresses the same "getting lost" risk without that arbitrary limit.
- *Reusing the existing danger/invalid visual treatment for the WebGL-unsupported state* — rejected: conflates an environment capability fact with a user-correctable configuration mistake, which the frontend-design consultation flagged as actively misleading once both states exist in the same kit.
- *Configurable elevation clamp (an attribute like `min-scale`/`max-scale`)* — rejected: no acceptance criterion needs tuning it, and the entire point of the clamp is preventing pole-flip disorientation, which a wide/near-zero configured margin would defeat.
- *An on-screen axis/compass gizmo in v1* — rejected as premature: not required by any acceptance criterion; deferred with an explicit constraint (DOM/CSS overlay only, never drawn into the consumer's canvas) recorded now so it doesn't get built ad hoc and inconsistently later by each consumer.
