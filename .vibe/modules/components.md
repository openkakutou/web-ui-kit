# Module: components
**Role:** The layout-shell Web Components (panel, toolbar, tabs, app shell) plus the form/input Web Components (file drop-zone, slider, color picker, radio group, button) and the overlay Web Component (dialog) that give consuming apps their screen structure, common input widgets, and modal surfaces, each usable standalone or composed together.
**Files:** `src/components/panel.ts`, `src/components/toolbar.ts`, `src/components/tabs.ts`, `src/components/app-shell.ts`, `src/components/file-drop-zone.ts`, `src/components/file-drop-zone-accept.ts`, `src/components/slider.ts`, `src/components/slider-config.ts`, `src/components/color-picker.ts`, `src/components/color-picker-color.ts`, `src/components/radio-group.ts`, `src/components/radio-group-options.ts`, `src/components/button.ts`, `src/components/dialog.ts`, `src/components/index.ts`
**Exports:** `WuikPanelElement` (`<wuik-panel>`), `WuikToolbarElement` (`<wuik-toolbar>`), `WuikTabsElement`/`WuikTabPanelElement` (`<wuik-tabs>`/`<wuik-tab-panel>`), `WuikAppShellElement` (`<wuik-app-shell>`), `WuikFileDropZoneElement` (`<wuik-file-drop-zone>`), `WuikSliderElement` (`<wuik-slider>`), `WuikColorPickerElement` (`<wuik-color-picker>`), `WuikRadioGroupElement`/`WuikRadioOptionElement` (`<wuik-radio-group>`/`<wuik-radio-option>`), `WuikButtonElement` (`<wuik-button>`), `WuikDialogElement` (`<wuik-dialog>`) — each self-registers via `customElements.define` as a side effect of import; `index.ts` is the barrel re-exporting all of them.
**Public contract:** See `docs/api.md` for the full slot/attribute/event/keyboard reference. Every component styles itself entirely via `--wuik-*` tokens on `:host` (or shadow-internal selectors) — no consumer CSS is required and every color follows the active `data-theme` automatically, since no component hardcodes a literal color. Pure attribute-validation logic for the form/input components (`file-drop-zone-accept.ts`, `slider-config.ts`, `color-picker-color.ts`, `radio-group-options.ts`) is kept in its own module, separate from DOM/event glue, so validation rules are tested without mounting a component. `<wuik-tabs>`'s `orientation="vertical"` attribute lays the tab strip out as a column and swaps its active arrow-key pair to ArrowUp/ArrowDown (any other value, including omitted, falls back to horizontal/ArrowLeft-Right both visually and behaviorally, read from the same check); `aria-orientation="vertical"` is set on the tablist only in that mode, mirroring `<wuik-button>`'s asymmetric `aria-pressed` forwarding — see `.vibe/decisions/020-tabs-vertical-orientation-and-baseline-shift-avoidance.md`. `<wuik-slider>`/`<wuik-color-picker>`/`<wuik-radio-group>`/`<wuik-dialog>`'s translated text goes through `modules/i18n.md`'s `t()`, re-rendering live on a locale change (subscribed in `connectedCallback`, unsubscribed in `disconnectedCallback`). `<wuik-radio-group>` reads its `<wuik-radio-option>` children reactively via `slotchange` (mirroring `<wuik-tabs>`/`<wuik-tab-panel>`) rather than an attribute, since option labels are arbitrary end-user-visible text — see `.vibe/decisions/016-radio-group-options-as-light-dom-children.md`. `<wuik-button>`'s boolean `pressed` attribute layers a token-driven pressed style on top of any `variant` and forwards `aria-pressed` to the native button asymmetrically (`"true"` when present, removed entirely — not `"false"` — when absent), so a plain non-toggle button never gains toggle semantics; see `.vibe/decisions/018-button-pressed-state-design.md`. `<wuik-dialog>` wraps a real `<dialog>` element but never relies on the browser alone for focus move/trap, Esc-to-close, backdrop-click-to-close, or focus-restore — all hand-rolled in the component's own JS, feature-detecting native `showModal()`/`close()` as a pure rendering enhancement, since `jsdom` (this project's test environment) implements neither at all; see `.vibe/decisions/019-dialog-manual-behavior-over-native-showmodal.md`.
