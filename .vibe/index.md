## Modules
- [`modules/package.md`](modules/package.md) — package entrypoint, re-exports the public API surface (version constant, layout/form components, canvas controls) and side-effect-imports the design tokens CSS
- [`modules/components.md`](modules/components.md) — the layout-shell Web Components (panel, toolbar, tabs, app shell) and the form/input Web Components (file drop-zone, slider, color picker, button), each usable standalone or composed together
- [`modules/canvas.md`](modules/canvas.md) — reusable zoom/pan/reset-to-fit viewport controls (`<wuik-viewport>`) for wrapping any canvas-based preview
- [`modules/canvas3d.md`](modules/canvas3d.md) — reusable orbit/pan/zoom 3D camera controls (`<wuik-viewport-3d>`) for wrapping any 3D-rendering preview (first: Ikemen GO 3D model-based stages)
- [`modules/tokens.md`](modules/tokens.md) — design tokens (color light/dark, spacing, typography) as CSS custom properties, the foundation layer components style themselves with
- [`modules/publish.md`](modules/publish.md) — pack-content/metadata guards and the `smoke/` fixture gating the tag-triggered npm publish pipeline

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`, using Vitest + jsdom
- Vite **library mode**: single ESM bundle `dist/web-ui-kit.js` built from `src/index.ts`, exposed via the package `exports` field — no `index.html`, no dev server
- CSS reached from the JS entry (`src/index.ts` → `src/tokens/index.css`) is extracted by Vite into its own `dist/*.css` file rather than injected at runtime; each such stylesheet gets its own `exports` subpath (`./tokens.css`) so consumers can import it explicitly
- `test.css: true` is set in `vite.config.ts` so CSS custom properties can be asserted on for real via `getComputedStyle` under jsdom, instead of Vitest's default CSS-import mocking
- Design tokens are namespaced with a `--wuik-` prefix and split into semantic (not primitive) color tokens, plus theme-independent spacing/typography tokens; only the aggregating `index.css` per token group is a supported import path — sub-files are a private implementation detail
- CLI-facing `.mjs` scripts (`src/publish/verify-pack.mjs`) import their logic straight from a co-located `.ts` module and are run via `node --experimental-strip-types`, so the CLI wrapper and its Vitest-tested pure logic never drift into two copies
- Parsing a third-party CLI's JSON output (`src/publish/parse-pack-output.ts`'s `extractPackedFilePaths`, consumed by `verify-pack.mjs`) is kept in its own pure function rather than inlined into the guard that uses it, specifically so it can absorb an upstream shape change (`npm pack --json`'s array-vs-object-keyed top level across npm major versions) in one place, tested independently of the guard logic that consumes its result
- GitHub Actions in `.github/workflows/` are pinned to a commit SHA (with a version comment), never a floating tag — required by any workflow touching a publish-capable secret
- Every Web Component (`src/components/*.ts`) self-registers with `if (!customElements.get("wuik-x")) customElements.define("wuik-x", ...)` at module scope — idempotent against being imported more than once — and styles itself entirely via `--wuik-*` tokens on `:host`/shadow-internal selectors, never a literal color, so it follows the active theme automatically with no consumer CSS
- Components with dynamic light-DOM children (`wuik-tabs`, `wuik-app-shell`'s named slots) react to `slotchange` on their own shadow `<slot>` rather than a `MutationObserver` on themselves, and also run that same handler once from `connectedCallback` for the initial render — needed because a parent custom element's `connectedCallback` fires *before* its children's (tree order), so a child's own state (e.g. an auto-generated `id`) cannot be relied on yet at that point; anything a parent needs from a child is derived/assigned by the parent itself instead
- `jsdom` does not apply Shadow DOM `<style>` rules to computed style, and separately never resolves `var()` in computed properties — component tests assert shown/hidden state via the class the component toggles and assert token usage against the shadow stylesheet's **text**, never via `getComputedStyle` (see `.vibe/decisions/006-token-css-tested-structurally-not-computed.md`); real rendered/computed correctness is checked once per component with a real-browser (Playwright) smoke pass during development, not by the test suite
- An unstyled `<slot>` defaults to `display: contents` in real browsers, making it transparent to CSS Grid placement — a `<slot>` used as a named grid area (`wuik-app-shell`) needs an explicit `display: block` or its `grid-area` has no effect and its slotted children fall back to grid auto-placement instead
- Attribute-validation logic for a component (accept-pattern matching, numeric range resolution, hex color parsing) is kept in its own pure module, separate from the component's DOM/event glue, and given its own test file — so validation rules are tested directly without mounting a custom element (`file-drop-zone-accept.ts`, `slider-config.ts`, `color-picker-color.ts`)
- A malformed *configuration* value (non-numeric slider range, malformed color string) falls back to a default **and** sets a visible `is-invalid` state (class + `aria-invalid` + inline error text); a well-formed value merely outside a valid range is just clamped silently, matching native `<input>` behavior — the two cases are deliberately not conflated (`.vibe/decisions/007-form-input-components-shared-conventions.md`)
- `jsdom` does not implement `DataTransfer` — a component's `drop` handler is tested by dispatching a plain `Event` with a stubbed `dataTransfer: { files }` property via `Object.defineProperty`, rather than constructing a real `DragEvent`
- A component that must never fabricate a visible label for empty/missing content (`wuik-button`) instead logs a `console.warn` and shows a non-labelling visual indicator — deliberate, not a debug leftover to be stripped
- A component wrapping arbitrary consumer-rendered content (`wuik-viewport`) never touches that content's pixels: it applies a CSS `transform` to a wrapper around its default slot and exposes the numeric result via a getter + change event, so the integration contract needs zero cooperation from the consumer's own rendering code (`.vibe/decisions/008-viewport-controls-integration-contract.md`)
- A component that intercepts the mouse wheel (`wuik-viewport`) only does so once it holds focus (`document.activeElement === this`, retargeted correctly to the host across the shadow boundary) — an unfocused wheel pass-through is left un-prevented so the component never traps the page's own scroll
- Constructing a component's class via `document.createElement(tag)` (or HTML-parser upgrade) when that class is imported from a **separate** module file loses access to its own methods/accessors under this project's Vitest+jsdom+esbuild combination — confirmed not a real defect (a plain Node+`jsdom` script and a real-browser Playwright pass both work correctly); the test-side workaround is constructing with `new TheElementClass()` instead. See "Constructing a component imported from another module" in `docs/testing.md`.
- `--wuik-color-danger` is never used as text color: as foreground-on-surface it falls short of WCAG AA (4.5:1) in the light theme. Invalid-state message text (`wuik-slider`, `wuik-color-picker`) uses `--wuik-color-text` instead, while the invalid state still signals non-verbally via a `--wuik-color-danger` border/outline plus `aria-invalid` (`.vibe/decisions/009-error-text-uses-text-token-not-danger.md`). The full verified contrast-pair set — including `text-secondary` and the focus ring's separate 3:1 non-text check — lives in `src/tokens/index.test.ts`.
- An interactive form/input component that wraps a native control with no visible text of its own (`wuik-slider`, `wuik-color-picker`) accepts an optional `label` attribute forwarded to the native control's `aria-label`; omitted, no accessible name is fabricated (`wuik-button`'s stricter empty-slot rule is the same principle applied where there's no native control to fall back on).
- WebGL feature detection (`detectWebglSupport` in `src/canvas3d/orbit-camera.ts`) takes an injectable canvas-factory parameter defaulting to a real `<canvas>` — under this project's `jsdom` test environment, the real default path already exercises the "unsupported" branch for free (`jsdom` implements no WebGL context at all), while the component's own tests (`viewport-3d.test.ts`) simulate "supported" by stubbing `HTMLCanvasElement.prototype.getContext` for the scope of those tests. See "Simulating WebGL support/absence in jsdom" in `docs/testing.md`.
- A component whose failure mode has no bounded, config-driven recovery (`wuik-viewport-3d`'s pan, deliberately unbounded — decision `010`) mitigates "getting lost" by making its reset action always-visible built-in shadow-DOM chrome, not just a keyboard shortcut or an optional consumer-provided `overlay` slot — the built-in affordance is the actual safety net, the keyboard/method forms are additional entry points to the same action.
- An environment-capability fallback (`wuik-viewport-3d`'s "WebGL unsupported" state) is deliberately styled and marked up (`role="status"`, neutral/muted border) as visually and semantically distinct from the existing malformed-*configuration* invalid state (danger-adjacent border + `aria-invalid`, decision `007`) on the same component — the two failure causes (an environment fact the consumer cannot fix vs. a user/config mistake that can be corrected) are never conflated (decision `010`).
- UI-feel constants that only exist to tune how an interaction *feels* (drag-to-angle speed, keyboard step size) live in the Web Component file (`viewport-3d.ts`), not the pure geometry module (`orbit-camera.ts`) — keeping the math module's public surface expressed purely in domain units (radians, distance) independent of pixel-tuning choices, mirroring the existing pure-math/DOM-glue split (`modules/canvas3d.md`, `modules/canvas.md`).
- The exported `version` constant (`src/version.ts`) is read directly from `package.json` via a JSON import (`with { type: "json" }`), never a hand-maintained literal — a hardcoded copy is what drifted out of sync and broke the real `v0.4.0` npm publish (backlog item `008`). `version.test.ts` guards against a hardcoded literal being reintroduced by asserting the source contains no bare semver string.
